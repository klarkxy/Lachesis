# 为什么不用现有多智能体框架

状态：决策记录，2026-10-01。基于当日关于多智能体协作路径的讨论。

## 背景

Lachesis 需要支持多 harness（DSH、Codex、Claude Code 等）的协调。现有开源多智能体框架（AutoGen、MetaGPT、CrewAI）已经很成熟，为什么不直接用？

## 核心冲突：设计哲学相反

### 现有框架的假设

1. **agent 是无状态的函数，被框架调用**
2. **人只在启动时定义任务，之后全自动**
3. **失败了就整个流程重跑**

### Lachesis 的需求

1. **人能随时接管、改方向**
2. **失败后从检查点续跑，不是从头来**
3. **agent 的状态对主智能体和人都透明**
4. **子智能体之间能直接通信，不必绕中央路由**

这两种哲学**根本上矛盾**：
- 框架要的是「把人排除在循环外」
- Lachesis 要的是「失败能优雅降级、人能随时介入」

## 用框架会遇到的具体问题

### 1. 实现检查点续跑要和框架对抗

**需求**：子任务跑了 20 分钟被 crash-recovery 杀了，想从第 18 分钟的检查点续跑。

**用框架的困境**：
- 框架假设任务定义是不变的、一次跑完的
- 要让 agent 写检查点？得 hack 框架的执行循环
- 要从检查点续跑？框架的状态机不支持「跳过前面几步」

**自己搓**：
```typescript
// 子智能体主动上报检查点
await lachesis.checkpoint(task.id, {
  stage: "wrote_tests",
  artifacts: ["tests/dashboard.rs"]
})

// 失败后从检查点续跑
await lachesis.resume(task.id, { from: "wrote_tests" })
```

### 2. 人工介入要打破框架的控制流

**需求**：子任务跑偏了（比如跑了另一棵代码树的测试），人想中途改方向。

**用框架的困境**：
- 框架假设任务定义在启动时就固定了
- 中途改方向 = 停掉整个流程，改定义，重新启动
- 20 分钟的进度全部白费

**自己搓**：
```typescript
// 人随时能查状态
const status = await lachesis.query(task.id)
// 发现不对，暂停
await lachesis.pause(task.id)
// 人工调整代码/方向
// ...
// 继续
await lachesis.resume(task.id)
```

### 3. 状态透明要绕开框架的封装

**需求**：主智能体想知道「子任务现在在干什么、最后一次写文件是什么时候」。

**用框架的困境**：
- 框架的状态在内部，外部只能看到「running」或「done」
- 要知道细节？只能解析日志，或者 hack 框架的内部 API

**自己搓**：
```typescript
interface TaskStatus {
  stage: "compiling" | "testing" | "blocked" | "done",
  lastCheckpoint: {
    at: "15:08",
    stage: "cargo_check_started",
    pid: 12345
  },
  alive: true
}
```

### 4. peer 通信要打破中央路由

**需求**：两个子智能体之间要直接通信（比如「一个生成代码，一个审查，审查有问题直接告诉生成者」）。

**用框架的困境**：
- 框架假设所有消息都走中央调度器
- 子 agent 之间不能直接说话
- 必须「子 A → 调度器 → 子 B」，延迟高、调度器成瓶颈

**自己搓**：
- 主智能体 → 子智能体：走 Lachesis 调度
- 子智能体 ↔ 子智能体：走各 harness 原生能力（`mavis session send`、`dsh session send` 等）
- Lachesis 只提供查询接口，不包办通信

## 成本对比

### 用框架的成本

**表面上省事**：
- 不用自己写 LLM 调用封装
- 不用自己写状态持久化

**实际上更贵**：
1. **对抗框架的成本**：检查点、续跑、人工介入都要 hack
2. **背负框架的依赖和抽象**：最后发现「用框架的部分」只剩下 LLM API 调用
3. **受限于框架的假设**：「全自动、一次跑完、失败重来」这些假设改不掉

### 自己搓的成本

**核心能力**（1000 行代码够了）：
1. **LLM API 调用 + 工具绑定**：OpenAI SDK、Anthropic SDK 都是现成的（300 行）
2. **状态持久化**：SQLite 或 JSON 文件（200 行）
3. **通信原语**：消息队列 + file watcher（200 行）
4. **契约和验收**：任务定义 + 执行检查（300 行）

**复杂度在哪里**：
- agent 的能力定义（工具集、提示词、决策逻辑）
- **但这部分用框架也得自己写**

## 什么时候该用框架

如果目标是：
- **快速验证某个协作流程的可行性**（比如「三个 agent 能不能协作写一个前端页面」）
- **不关心失败恢复、不关心人工介入**
- **愿意接受框架的抽象和限制**

那用现成的省事。

但如果目标是：
- **探索「agent 失败后怎么优雅降级」的最佳实践**
- **让人能随时接管、改方向**
- **让 agent 的状态对其他工具（比如 MiniMax Code、IDE）透明**

那现有框架 **会成为障碍**，因为它们的设计哲学就是「把人排除在循环外」。

## Lachesis 的选择

**自己搓，但分阶段验证**：

### Phase 1：最小可用内核（1 周）
- 一个 LLM 调用封装（支持工具）
- 一个简单的状态存储（SQLite 或 JSON）
- 一个消息队列（agent 之间发消息）
- **验证目标**：两个 agent 能协作完成一个简单任务（比如「一个生成代码，一个审查」）

### Phase 2：检查点和续跑（1 周）
- agent 每完成一个子步骤就写检查点
- 失败后能从最近检查点续跑
- **验证目标**：一个 20 分钟的任务被中断后，能在 2 分钟内续跑

### Phase 3：人工介入（1 周）
- 提供 CLI/Web UI，让人能看到当前状态
- 人能在任何检查点「暂停 → 改代码/改方向 → 继续」
- **验证目标**：人能在中途改一个 agent 的输出，其他 agent 能基于新输出继续

### Phase 4：契约和验收（可选）
- 任务定义里声明交付物和验收条件
- 自动跑验收，失败了通知人或 fallback 到备选方案

**每个阶段结束都有可演示的原型**，而不是「憋 3 个月，最后发现方向错了」。

## 结论

**不用现有框架，自己搓协调层。**

理由：
1. **现有框架的设计哲学和 Lachesis 的需求相反**（它们要全自动，Lachesis 要能随时人工介入）
2. **Lachesis 要的核心能力（检查点、续跑、透明状态）都不是框架提供的**
3. **从零搓的成本没那么高**，1000 行代码就能跑通核心逻辑
4. **完全控制架构**，后续加新能力不用和框架抽象对抗

如果只是要 **「快速糊一个多 agent demo」**，那用 AutoGen 省事；但 Lachesis 要的不是 demo，而是一个 **「能用在真实场景、失败能恢复、人能介入」** 的系统——那就别被框架绑住。
