# 00 · 冻结决策

## 证据等级与冲突处理

- **已确认**：用户明确提出，或在对应架构建议后表示「OK，没什么问题」。
- **实现建议**：为可施工性补充的工程方案，可以在不破坏已确认语义的前提下调整。
- **待定／后续**：讨论未定，不是第一版必须完成的承诺。

优先级：用户最后一次明确修正 ＞ 已确认产品语义 ＞ 本包实现建议 ＞ 原型图中文字 ＞ 早期探索。

## 已确认的产品与架构方向

| 编号 | 决策 | 施工含义 |
|---|---|---|
| D01 | 独立的工单式 Swarm 管理器 | 外部主线程向项目提交任务，服务负责调度与执行记录 |
| D02 | 第一阶段只支持 dsh | 暂不实现多 CLI 通用适配，也不迁到 Pi 重做 |
| D03 | 沿用 dsh 插件式架构 | 复用运行时与插件能力，不另写模型工具循环 |
| D04 | 不要求管理器本身是一个主 LLM | 确定性程序可以负责工单、领取、调度与状态 |
| D05 | Profile 是可复用配置 | 不把一个 Profile 当成一位只能接一单的常驻员工 |
| D06 | 同一 Profile 能启动多个实例 | 多实例各有执行身份、会话与工单关联，数量受资源限制 |
| D07 | 初期行为配置为供应商／模型＋思考强度 | 不把 persona、技能包、工具权限、长期记忆等扩张进 Profile 初始表单 |
| D08 | 工单完成后可由主 Agent 评价 | 评价属于工单；Profile 分数从工单评价汇总 |
| D09 | 用得顺手可显式指定 Profile | 必须保留明确选人的路径，不能强制完全自动派工 |
| D10 | 「监工台」仅作为设计方向，不作为产品术语 | 可借用派工／查看执行／验收的隐喻，但不得进入产品名、页面名、导航、UI 文案、包名、仓库名或素材品牌 |
| D11 | 头像参考用户提供的极简 Q 版图 | 大头、简化椭圆眼、平涂、低对比细节，服务于识别 |
| D12 | 头像绑定 Profile | 同一 Profile 的并行实例不随机换脸，也不以头像推断能力 |
| D13 | 后续考虑批量生成头像预制 | 可能用本地模型或 GPT；不是第一版自动生图或实时生图需求 |
| D14 | 正式产品名为 **Lachesis** | DSH 只是第一阶段执行底座，不进入产品名；项目、文档、包和 UI 统一使用 Lachesis |

D04 与「服务独立于主会话」来自已接受的 dsh-only 方案。独立是产品与生命周期边界，不要求马上建设远程集群。

## 原始表述摘录

> 「主线程（和本应用通常无关）向这个应用对应的项目里发issue」

> 「agent应该只是一种profile，也就是可以以同样的profile拉起很多个不同的agent，分别完成各种任务」

> 「当然打分是针对工单的，然后聚合起来就是某个profile的分数」

> 「初步的可选设定项就是模型（供应商/模型）+思考强度」

> 「不要太游戏化了！这毕竟还是一个生产力工具！」

> 「后续会考虑用本地模型或者gpt来批量生成一批作为预制，绑定在profile上。」

这些摘录来自本次对话，用于施工时解决歧义。

## 名称与视觉的冻结程度

正式产品名已确定为 **Lachesis**。DSH 不进入产品名。仓库名建议使用 `lachesis` 或其组织内可用变体，域名可用性另行确认。

「监工台」只作为设计方向关键词保留在文档中，用于解释派工、查看执行与验收的交互隐喻；不得作为产品名、页面名、功能名、导航项、包名、仓库名或素材品牌。早期的「派工台 / DispatchHub」与「帕鲁监工台 / PAL SUPERVISOR」均为已弃用探索。

用户最后确认的是生产力取向与头像风格，未逐项批准最后四张图里的导航、颜色、评分权重、统计面板和数据。因此不能把整张图当成完整 PRD。

## 调度策略的冻结程度

用户最初提出轮询／随机／LLM 指定等方式，并保留显式点名。归档为「调度可扩展方向」。其中：

- 轮询是发现新任务的机制；轮转、随机和 LLM 推荐是选 Profile 的机制。
- 第一版具体默认算法尚未定案。
- 显式指定是必须保留的产品能力。
- 「必须使用」与「优先使用」的区别是建议补充的接口语义，见接口文档。

## 已被后续方向替代或排除的内容

不做一开始就管理 Codex、Claude Code、Pi 等多种 CLI；不采用重型「AI 公司」组织架构；不把每个 Agent 永久人格化；不将实例直接计分；不把游戏化监工场景作为主界面；不因为图中出现某项配置就扩大 Profile 的初始配置范围。
