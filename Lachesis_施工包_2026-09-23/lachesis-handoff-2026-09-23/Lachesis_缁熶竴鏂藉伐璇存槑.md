# Lachesis · dsh 工单 Swarm 施工包

**讨论归档：2026-09-23｜版本：v0.1｜性质：施工交接，不是已经实现的软件**

> 将任务发成工单；从可复用 Profile 启动 Agent 实例；交付后对工单评价；把这些评价汇总为 Profile 的使用履历。

## 先读这一页

产品正式名为 **Lachesis**。名称取自希腊神话中负责丈量与分配命运之线的 Lachesis，与系统“接收工单、选择 Profile、启动实例、记录结果”的职责相呼应。

「监工台」只保留为**设计方向关键词**，用于描述“派工、看执行、验收”的交互隐喻；它不是产品名、页面名、功能名、导航项、包名、仓库名或任何对外 UI 文案。

本包只归档今天这条对话里的工单 Swarm 项目，不包含其他项目，也不代表已经创建仓库、部署服务或完成代码。

**最新明确要求优先于早期建议，也优先于任何生成原型中的文字。**

最小闭环：

`外部主 Agent 提交工单 → 选择 Profile → 启动一个实例执行 → 交付 → 主 Agent 验收并评价工单 → 聚合到 Profile`

必须保持的六点：

1. 第一阶段只支持 dsh，整体沿用其插件式架构；不另做一套模型调用和工具循环。
2. 管理器独立于委托方主会话。主线程可以来自其他应用，不强制迁入本系统。
3. Profile 是配置，不是一个常驻的「员工」。同一 Profile 可以启动多个独立 Agent 实例。
4. 初期行为配置只有供应商／模型与思考强度；名称与头像是展示元数据，不是新增行为配置。
5. 评价对象是工单，不是临时实例。Profile 分数由工单评价聚合，重试和多实例不能重复刷样本。
6. 不过度游戏化；使用用户提供的极简 Q 版头像风格参考，头像绑定 Profile。同 Profile 的实例使用同一头像，以实例 ID 区分。

# 01 · 产品与范围

## 一句话产品定义

一个独立运行、以工单为协作单位、由 dsh 执行任务的生产力工具。用户维护少量可复用 Profile；调用方按项目提交工单；系统从 Profile 启动临时 Agent 实例；任务被验收和评价后，留下可查询的执行记录与 Profile 履历。

## 主要使用者

委托方可以是外部主 Agent，也可以是人类操作员。执行实例负责具体任务，管理服务负责保存工单与执行状态。委托方主 Agent 与 worker 使用的模型没有必须强弱排序的限制。

生产力工具不应强迫用户长期盯着监控页。常见流程应能通过少量工具／API 完成，UI 用来配置、查看异常、检查结果与人工介入。

## 三条必须跑通的流程

### A. 点名执行

用户已有「白露」Profile，配置为某供应商下的模型与指定思考强度。外部主 Agent 向某项目创建工单，写清目标、输入和验收标准，指定该 Profile。服务接收后返回工单 ID，领取任务并启动实例，最后生成交付记录。委托方查询或接收事件，决定接受或返工，再对工单评价。

### B. 同 Profile 并发

两个不同工单都选「白露」。在资源许可时，同时启动「白露 · 实例 A」与「白露 · 实例 B」。两者使用相同 Profile 配置与头像，但会话、工作状态和结果互不混淆。取消 A 不得取消 B。

### C. 验收、返工与聚合

执行结束不自动代表验收通过。工单先进入待验收；委托方可以补充要求、返工或接受。一次工单的多次执行不应变成多条独立质量样本。聚合结果应能追溯到具体工单评价，而不是仅显示一个来源不明的分数。

## 第一版建议范围

以下拆分是施工建议，不新增已确认行为配置。

| 模块 | 建议第一版能力 |
|---|---|
| 项目 | 名称、输入／工作区关联、工单归属 |
| Profile | 名称、头像、供应商、模型、思考强度；可复制、停用 |
| 工单 | 标题、描述、输入引用、验收标准、状态、Profile 选择 |
| 执行 | 启动实例、观察状态、补充消息、取消、超时处理、结果归档 |
| 交付 | 摘要、文件或补丁引用、验证证据、运行记录 |
| 评价 | 对工单评分与写意见，聚合到对应 Profile |
| 调度 | 显式指定；自动模式先采用一个简单、可解释的策略 |
| UI | 工单列表／详情、Profile 列表／编辑、执行实例查看 |

运行日志、凭据保护、并发约束属于基础工程，不应因此把复杂权限和预算编辑器塞进 Profile 页面。

## 明确不纳入初始必做范围

不做多 CLI；不做自治公司与组织树；不做长期人格和共享记忆；不做自动自我修改；不做工作者养成；不做复杂绩效排行榜；不做根据头像自动推断岗位；不做自动批量头像生成界面；不承诺任何供应商订阅都可以无条件转接到 dsh。

LLM 路由、按历史反馈自适应选人、更复杂的工作流、外部 GitHub／Linear 同步、远程执行与账号额度可视化都可后续演进，不能阻塞点名执行闭环。

## 外部调用方的交互原则

提交后立即得到可查询的 ID，不让 HTTP 请求或工具调用一直绑定完整执行时长。调用方可以选择查询或等待事件；退出后也能重新读取结果。

不能承诺给任意外部 CLI 自动插入消息。调用端有事件接收能力时可以推送，否则通过查询／等待完成。通知不是结果的唯一存放位置。

每张工单保留委托来源与调用方关联 ID。重试提交应支持幂等；跨项目／跨调用方数据不能因复用 Profile 混在一起。

## 产品指标

优先记录真实的已评工单数、待验收数、执行耗时、失败原因和并发实例数。供应商实际提供的用量可记录；未知成本应显示未知，不能凭 token 数臆造账单。

不以图中的「28% 完成」「预计两小时」「96.8 置信度」作为必须实现的指标。没有可靠依据时，显示已发生的步骤和最近活动即可。

# 02 · 架构建议

**本章是已确认方向下的实现建议。模块名、数据库、进程边界和 SDK 调用需在锁定的 dsh 版本上验证。**

## 1. 分为控制服务与执行运行时

控制服务持有项目、工单、Profile、领取关系、执行记录、评价与通知记录。执行运行时复用 dsh 的模型调用、工具执行、会话和插件机制。

```text
外部主 Agent / 人类客户端
       │ 提交、查询、补充、取消、验收、评分
       ▼
Lachesis 服务（dsh / Cordis 插件式应用）
       ├─ 工单与 Profile 存储
       ├─ 调度与领取
       ├─ 运行记录、交付物、评价
       └─ 事件与客户端接入
       │
       ▼
DshExecutor（第一版唯一执行器）
       ├─ 执行 A：Profile X / 独立会话
       ├─ 执行 B：Profile X / 独立会话
       └─ 执行 C：Profile Y / 独立会话
```

主 Agent 不需要常驻 Lachesis。工单不会因委托方对话结束而被删除或取消。控制服务是否与 worker 共进程，是实现选择，不改变独立工单服务的语义。

## 2. 初期少量插件，内部清楚分层

建议先有 `swarm-service` 与 `swarm-tools` 两个入口，名称仅为草案。

`swarm-service` 对外提供任务管理服务；内部按普通代码模块分成存储、调度、执行和评价。`swarm-tools` 把经过授权的操作暴露给调用方 Agent。UI 作为服务客户端，不自行实现另一套工单状态机。

不要为了「一切皆插件」把每个数据库表、按钮或排序函数都拆成 npm 包。只有存在独立生命周期、替换需求或第三方实现时才抽出扩展接口。

插件卸载、重载和服务关闭必须有清楚的处理规则。持久化业务状态不能只保存在某个插件的内存对象里。建议正在执行的 worker 使用固定配置，配置变更影响新 Run，不热改旧 Run。

## 3. 工单、执行记录、实例、会话分开

- **Issue**：需要交付什么，属于哪个项目，谁验收。
- **Run**：某 Profile 配置快照对该工单的一次执行尝试。
- **Instance**：实际运行中的 Agent 执行实体，临时存在。
- **Session**：dsh 保存上下文与执行过程的会话资源。

第一版建议一个 Run 对应一个实例和一个独立会话，减少关联歧义。这是可调整的实现策略，不限制未来一个工单有多次 Run。

服务只保存必要引用，不复制一套完整 dsh 会话存储。会话历史不是工单数据库，反之亦然。不要把某个主会话的内部子任务列表当成长期项目任务账。

## 4. 只保留一个薄执行接口

建议的应用接口，不是 dsh 原生方法：

```text
Executor.start(runSpec)          → handle
Executor.observe(handle)        → events / state
Executor.send(handle, message)  → receipt
Executor.cancel(handle)         → cancellation outcome
Executor.collect(handle)        → delivery + evidence
```

第一版只有 DshExecutor。其他模块不能依赖 dsh 私有类、私有会话文件字段或终端输出的偶然格式。以后出现真实需求，再实现其他 runtime。

对恢复、运行中消息插入、取消等能力，实际支持就声明；不支持要明确失败。不要接受参数后静默忽略。禁止通过 `process.chdir()`、改共享环境变量或修改全局默认模型来实现并发隔离。

## 5. dsh 接口验证是开工第一步

本次讨论包含进程内 Agent 接口、subagent、SDK 等多条路径，但没有完成运行对照测试。前文一些接口示意和引用不能直接当代码复制。

特别需要验证：

1. 指定 provider、model 和思考强度是否真实生效；不支持的值是否明确报错。
2. 一个 worker 的模型配置、工作目录和凭据是否影响其他 worker。
3. 当前 SDK／宿主接口能否对单个任务取消，而不是关闭整个共享进程。
4. 完成事件到底表示收到了消息、一个 turn 结束、Agent 空闲，还是任务交付。
5. 同一会话多条消息的结果是否能可靠归因；不能时使用单 Run 独立会话。
6. 恢复和重启能否继续，或者只能标记中断并创建新的 Run。

前文读到的 SDK 文档曾明确区分「入队回执」与「结果」，并提示部分 wire 没有逐提示取消或会话关闭接口。必须以实际锁定版本复查。不能因为高层示例出现 `run()`，就假定它是严格一问一答的任务完成协议。

## 6. 第一版可用的部署取舍

建议单机、单控制服务，持久化数据库可先评估 SQLite。具体数据库没有被用户拍板，选择依据是领取事务、幂等、崩溃恢复与运维简单，而不是为了提前做集群。

worker 可使用独立 dsh 进程，或对可信任务使用进程内 Agent。独立进程便于单任务回收，但不是安全沙箱；同进程成本可能较低，但必须验证局部配置、取消和生命周期互不干扰。没有测量前不写性能结论。

对于并行写代码，建议每个 Run 准备独立工作区，并记录基准 commit。工作区隔离与操作系统沙箱是不同问题。合并和组合验证由交付／验收流程负责，不让所有实例直接写主分支。

## 7. 持久性与取消

领取应在事务中完成，避免同一候选被重复派工。每次 Run 有唯一身份与递增代次／租约标识。实例失联后可以回收；旧实例迟到的结果不得覆盖新的有效结果。

采用至少一次事件投递时，写入和回调都必须幂等。不要宣称任意外部副作用「恰好执行一次」。发布、付款、远端删除、合并等操作不属于默认自由重试范围。

取消请求、取消已生效和进程已退出不能混为一谈。超时后应停止或回收实际 worker，并标记已知副作用；不能只把 UI 状态改为取消。

重启后先读取未终结 Run，校验执行者存活状态，再决定恢复或终结。未知执行不能直接重新派工而忽略可能仍在工作的旧 worker。

## 8. 配置与账号

Profile 只引用已配置的供应商入口与模型，不保存明文密钥。供应商连接与凭据管理尽量复用 dsh 已有能力。实例获得最小必要凭据，日志、工单、导出包中不得包含密钥。

同一个订阅／账号被多个 Profile 引用时，建议在服务层共享并发上限或资源池。账号额度耗尽是可用性问题，不自动转换成工单质量差评。

名字、头像改变不应清空质量履历。模型或思考强度改变后，建议创建配置修订，旧 Run 和评价仍引用原修订。

## 9. 原生 subagent 与工单协作

第一版可暂不开放 worker 递归委派，避免管理器只计三个实例，而实例内部实际又开出许多子 Agent。

未来可区分：短时局部查询用原生 subagent；需要独立交付和验收的工作用子工单。两者共享资源与取消约束，不能出现两套互相看不见的并发账。

不需要为了任务服务先创建一个负责所有事情的「总经理 Agent」。LLM 选人可以是调度模块的可选能力，不是整个服务运转的前提。

# 03 · 数据与接口建议

**以下是应用领域模型草案，不是 dsh 的真实 SDK 类型；字段命名与存储可调整，语义不得违反冻结决策。**

## 1. 领域对象

| 对象 | 必要含义 | 与其他对象的关系 |
|---|---|---|
| Project | 项目身份及输入／工作区归属 | 包含工单 |
| Profile | 可复用配置的稳定身份、名称、头像 | 可有多个配置修订，启动多个实例 |
| ProfileRevision | provider／model／effort 的行为快照 | 被 Run 和评价归因引用 |
| Issue | 任务目标、验收标准、来源、状态 | 可有多次 Run，评价属于它 |
| Run | 一次实际尝试及使用的配置 | 关联实例、会话、交付记录 |
| Instance | 临时执行实体及存活状态 | 第一版建议一个 Run 一个实例 |
| Delivery | 摘要、文件、补丁、验证证据 | 由 Run 提交，等待验收 |
| IssueEvaluation | 对一张工单的评价及修订 | 归因到明确 Profile 修订 |
| AvatarPreset | 可选的静态头像素材 | Profile 引用，不决定模型能力 |

实例 ID 不是 Profile ID。不同 Profile 即使同模型同强度，也可以拥有不同展示身份；同 Profile 的不同实例不能被当成不同配置。

## 2. Profile 的初期配置边界

行为配置只有这三个选择：

```json
{
  "providerId": "provider-config-a",
  "modelId": "user-selected-model",
  "reasoningEffort": "provider-supported-value"
}
```

`name`、`avatarPresetId`、`id`、`revision`、创建时间是展示／管理元数据，不等于增加了角色提示词或工具行为。

思考强度候选由模型实际能力决定。没有暴露该能力的模型应显示「不支持／默认」，不能机械地替所有模型制造低、中、高三档。

供应商入口应能区分用户配置的不同端点或账号引用，不只保存「OpenAI」或「DeepSeek」这种品牌文本。敏感凭据保留在受控配置层，而非 Profile JSON。

## 3. 工单草案

```json
{
  "id": "issue-demo-001",
  "projectId": "project-demo",
  "title": "修复用户登录态异常失效",
  "description": "复现问题，定位原因，提交最小修复与回归测试。",
  "acceptanceCriteria": ["能复现原问题", "回归测试通过", "提交变更说明"],
  "inputRefs": [],
  "dispatch": {
    "mode": "require",
    "profileId": "profile-bailu"
  },
  "requesterRef": "external-client-demo",
  "clientRequestId": "demo-request-001"
}
```

此处 `require` 是建议语义：必须使用指定 Profile，不可静默换人。`prefer` 可以允许事先明确的回退；`auto` 由已启用策略选择。第一版不必同时实现全部策略。

时间限制、应用并发与凭据策略可由项目／服务默认值提供，不强迫用户创建 Profile 时填大量高级选项。

## 4. 建议状态流

```text
queued → running → awaiting_review → accepted
              ├→ needs_input → running
              ├→ failed
              └→ cancelled

awaiting_review → rework → queued → 新 Run
```

是否需要 draft、rejected 等额外状态可在施工中确定。

不变量：worker 的自述「完成」最多触发交付／待验收；只有被授权的委托方或审查者能执行验收操作。进程正常退出、测试通过、turn 结束都不是自动验收的同义词。

实例状态与工单状态分开。例如 worker 已退出，但工单仍然可以等待验收；一个工单返工产生新 Run，旧 Run 仍保留。

## 5. 评分归属与聚合

**已确认：对工单评分，聚合成 Profile 的分数。**

建议 IssueEvaluation 至少保存：工单 ID、评价修订、评价者、时间、分值、意见、归因 Profile ID／修订，以及作为证据的交付／Run 引用。Run 引用是证据，不把评分对象改成实例。

### 推荐的第一版规则，尚未由用户逐项拍板

- 评分采用 1–5 分，可附文本意见；不必一开始就有四维雷达或权重。
- 不强制接受时必须打分。未评分就显示未评分，不记为零分。
- 按有评价的独立工单做简单均值，显示样本数；不默认加权或隐藏计算过程。
- 返工多次、同 Profile 开多个实例，一张工单在当前汇总中只贡献一份有效评价。
- 修改评价时保留旧修订，但当前汇总只取该工单最新有效评价。
- 失败或未接受的工单可以保留实际评价；不能仅统计成功接受工单而制造幸存者偏差。
- 没有评价的失败不自动记为最低分。可另展示失败原因与运行可靠性记录。

建议计算：

`Profile 某修订平均分 = 属于该修订的有效工单评分总和 / 已评独立工单数`

跨修订总分可以展示，但需清楚标注；默认关注当前行为配置对应的履历，不把换模型前的表现无条件算成新模型能力。

### 多 Profile 参与一张工单

这是未完全定案的归因边界。第一版建议每次可评分交付有一个明确的主执行 Profile；其他尝试和独立审查仍留记录，但不把同一工单分数复制给所有参与者。

跨 Profile 换人、联合交付或并行竞赛时必须明确归因，不能暗中选择平均分、最后一次或所有人共享。需要各自独立评价的工作，可以后续拆成独立子工单。

## 6. 建议接口集合

名称仅用于应用设计，不承诺是已经存在的 dsh 工具。

| 操作 | 含义 |
|---|---|
| `profile.list/get/create/update/disable` | 管理可复用配置与头像元数据 |
| `issue.create/get/list` | 提交和读取工单 |
| `issue.comment` | 补充要求或持久讨论 |
| `issue.dispatch` | 指定或确认执行配置 |
| `issue.cancel` | 请求取消并返回实际执行状态 |
| `issue.accept` | 接受交付 |
| `issue.rework` | 发回修改，保留历史 |
| `issue.evaluate` | 评价工单并更新聚合 |
| `run.get/events` | 读取执行状态、证据和事件 |
| `events.wait` | 有超时与游标的等待，不作为唯一持久存储 |

创建工单和提交评价都应支持幂等。事件携带稳定 ID／游标，客户端断线重连能够补读，不重复通知成多张工单。控制服务统一鉴权，worker 不应自行调用验收和给自己评分。

## 7. 结果数据

建议 Delivery 包括可读摘要、产物引用、验证记录和使用的执行配置。验证记录区分「工具实际执行结果」与「模型自述」；不要把文本中写的 all tests passed 自动当成系统已经验真。

资源指标来自真实观测。无法取得 token 或成本时保留 null／未知。最终交付文案、日志与可下载文件应通过同一 Run 关联，不能混用其他实例的结果。

# 04 · UI 与原型纠偏

## 1. 视觉方向

**已确认：这是生产力工具，不是模拟经营游戏。**

产品 UI 统一使用 **Lachesis** 品牌。「监工台」仅是设计方向关键词：可以借用“派工、看执行、验收”的轻微趣味，但不得把这个词本身放进产品名、页面名、导航、按钮、状态、Logo 或其他可见 UI 文案。

以极简头像让不同 Profile 容易识别。主体使用清晰的工单、执行状态、交付和配置界面，不加入占据主屏的工厂场景、幻兽人物或经营系统。

最后一版参考图的浅色界面与头像方向可供参考，但蓝色主题、卡片圆角、侧栏布局并没有被正式冻结。施工应先保证密度、可读性、键盘操作与状态准确。

## 2. 头像规范

用户原图为四格极简 Q 版头像风格参考：大头近景、椭圆简化眼睛、少量腮红、平涂与柔和阴影，通过发色、发型、发饰或眼镜形成区分。无需识别或复用原图角色身份。

头像绑定 Profile，不绑定模型供应商，也不绑定每次临时实例。并行实例应显示同一头像＋Profile 名＋简短实例 ID，例如「白露 · #A17」「白露 · #A18」。不要给每个实例重新生成头像。

第一版建议从本地静态素材选择预制头像，并保存 `avatarPresetId`。后续再开发本地模型／GPT 批量生成与素材整理流程；不能自动引发 API 消费，也不要求创建 Profile 时在线生图。

原始四格图只作为风格参考归档，不视为已取得生产发布素材授权。正式发布应使用来源清楚的新预制素材。头像的可爱外观不应触发隐藏 persona、模型路由或岗位设定。

## 3. 最小页面集合

| 页面 | 主要信息 | 主要动作 |
|---|---|---|
| 项目／工单列表 | 状态、标题、所用 Profile、最近活动 | 新建、筛选、进入详情 |
| 工单详情 | 任务要求、验收标准、当前执行、交付、评价 | 补充、取消、验收、返工、评分 |
| Profile 管理 | 头像、名称、供应商／模型、思考强度、已评工单数 | 新建、编辑、复制、停用、选择头像 |
| 执行实例 | 实例 ID、Profile、关联工单、运行状态与时长 | 查看日志、结果、停止 |

概览是否独立一页待定。初期直接把工单列表作为首页也成立。评审可先放工单详情，不必为了凑导航单独造一套子系统。

## 4. Profile 编辑页的限制

行为编辑区域仅供应商、模型、思考强度；展示区域可有名称和头像。当前 Profile 实例数、已评工单数、分数可以是只读信息。

不照搬图中「擅长需求分析」「代码开发专家」「技能包」「职业标签」「高性能」等未经定义的能力。模型与思考强度不能根据头像自动设置。

模型不支持思考强度时，控件应禁用或展示供应商默认，而不是强行保存一个无法执行的值。

同 Profile 的实例列表必须使用一致的头像、供应商、模型和行为修订；只有明确记录的旧修订执行例外，而且 UI 应展示版本区别。

## 5. 工单与评价页的限制

执行完毕后是待验收，不是自动完成。评分属于工单，实例列表不提供独立「给此员工评分」按钮。

不默认采用原型里的加权聚合、不默认只计已接受工单、不默认四维评分。实际分值、样本与聚合规则按数据文档中的建议或后续决策实现。

截图里的人员聊天、产品经理、工程师和固定技术负责人只是示例，没有多用户组织架构需求。来源可以简单显示人类或外部主 Agent。

## 6. 执行实例页的限制

使用清楚的事实状态：已排队、启动中、运行中、等待输入、已结束、失败、取消等。没有真实进度模型时，不显示精确完成百分比或预计剩余时间。

CPU、内存、token、成本不是必须都做成图表；没有采集就不显示虚构读数。不要为了保留一个「空闲员工」面板而默认常驻大量 Agent 进程。

## 7. 页面结构参考（旧图已移除）

### 概览／工单首页

可参考：侧栏＋工单列表＋Profile 识别＋执行实例入口。

须纠正：同名 Profile 的头像、模型信息必须统一；顶部趋势、历史日期、平均分和成功率都是占位数据；删除未经定义的技能和职业标签。不要为了照抄仪表盘而优先做分析图表。

### Profile 管理

可参考：列表与编辑区、预制头像选择、关联实例列表。

须纠正：只保留初始三项行为选择；描述／标签不是既定智能能力；右侧加权和仅接受工单聚合说明未经确认；一个 Profile 的所有实例必须继承该 Profile 的头像与配置快照。

### 执行实例

可参考：实例 ID、Profile、工单、运行时长与详情抽屉。

须纠正：图中某些同名 Profile 显示不同供应商或模型，不能照搬；关系图中由一个 Profile 变出多种头像也错误。正确关系是同头像的多个实例，分别关联任务。CPU、进度和配额读数仅为占位。

### 工单与验收

可参考：任务描述、验收清单、关联文件、执行记录与验收动作。

须纠正：标题写同一 Profile 启动的实例时，不能给它们不同头像；评分区域与待验收状态应一致；多维评分不是冻结需求；文件、PR、测试数与模型名都是示例。

## 8. 已弃用的原型方向

早期「派工台 / DispatchHub」企业仪表盘太重；以「监工台」为显式品牌、以及「帕鲁监工台 / PAL SUPERVISOR」的 3D 小屋和动物工人方案都过度游戏化。这些只作为设计过程记录，不作为产品命名或施工素材。

最后一轮 UI 图片也因仍含过时品牌字样而从施工包与 Drive 素材目录移除。页面布局可参考本节的文字描述；重新出图时必须使用 **Lachesis**，或在纯线框阶段不显示品牌。出现矛盾时优先执行冻结决策。

# 05 · 施工计划与验收

**实施顺序建议，不是估时承诺。交接包没有执行代码施工。**

## M0 · 锁定运行时与验证接入

先选一个实际可安装的 dsh 版本／提交，记录插件组合和复现命令。用两个用户可用的模型配置验证 provider、model 和思考强度，不把原型的旧模型名写成默认值。

最小验证程序应能创建独立执行、读取事件、识别交付、取消其中一个而不影响另一个，并检查会话／工作目录／凭据是否串用。复查 SDK 的逐任务取消和消息结果归因能力。

交付：`docs/runtime-contract.md`、最小可复现测试、版本锁定。接口不存在时报告差异并选可行路径，不伪造 dsh SDK 方法。

## M1 · 数据与 Profile

落地 Project、Profile、配置修订、Issue、Run、Delivery、IssueEvaluation 的最小存储与迁移。实现 Profile 的三项行为配置、名称、静态头像绑定。

交付：可重启保存的配置与工单；同 Profile 多实例的数据模型；无明文密钥落入数据库导出或日志。

## M2 · 一张工单执行闭环

外部客户端提交工单并指定 Profile，服务持久接收、领取、启动 dsh、记录事实事件和交付，进入待验收。先跑通一条确定性流程，不优先做推荐算法和图表。

交付：提交、查询、取消、查看日志与交付的程序化入口；外部会话退出后仍能取回结果。

## M3 · 并发、失败与恢复

同 Profile 至少验证两个实例执行不同工单。实现并发约束、独立工作区、超时回收、重启校对、幂等提交与迟到结果保护。

交付：能证明不会混结果、重复领取、取消连坐和旧结果覆盖新结果的测试。

## M4 · 验收、返工、工单评分

增加接受交付、发回修改、评价工单以及 Profile 聚合。原型推荐的一星到五星只是建议，采用前应在项目决策中写明规则。

交付：一张工单多次 Run 只贡献一个当前有效评分；聚合有样本数和来源；未评分不算零分；换模型后历史能追溯。

## M5 · 最小 UI 与整理交付

工单列表／详情、Profile 管理、实例日志与结果。头像只从静态预制选择，遵循同 Profile 同头像。测试空状态、错误、排队、待验收和取消中的展示。

交付：可使用的最小界面、真实数据截图、启动说明、已知限制。最后再决定是否需要首页仪表盘、看板、多维评分和 LLM 路由。

## 核心验收用例

| ID | 场景 | 通过标准 |
|---|---|---|
| T01 | 外部创建工单 | 返回稳定 ID，可再次查询，无需保留提交连接 |
| T02 | 重复提交 | 同项目同幂等键不创建两张工单 |
| T03 | 点名 Profile | 实际使用被指定配置，不静默换模型或账号 |
| T04 | 指定配置不可用 | 明确等待／报错，原因可查看 |
| T05 | 不支持的思考强度 | 不伪装生效；使用前有明确校验反馈 |
| T06 | 同 Profile 两个实例 | 相同配置与头像，不同实例／会话／任务记录 |
| T07 | 并行任务隔离 | A 的文件、上下文和结果不混到 B |
| T08 | 局部取消 | 取消 A 不影响 B；实际执行得到停止或明确回收结果 |
| T09 | 提交方退出 | 已接受工单仍保留，可重新读取进展与结果 |
| T10 | 重复领取竞争 | 只有一个当前有效领取关系 |
| T11 | worker 失联 | 状态可恢复或明确终结，不永远假运行 |
| T12 | 旧实例迟到交付 | 不覆盖新 Run 的当前有效结果 |
| T13 | 服务重启 | 未终结 Run 先校对，不盲目重复启动 |
| T14 | 执行结束 | 进入待验收，不自动接受 |
| T15 | worker 自评／自验收 | 未授权操作被拒绝 |
| T16 | 返工 | 保留旧交付与 Run，建立新的尝试 |
| T17 | 工单多次执行 | 不按实例数量重复增加评分样本 |
| T18 | 未评分 | 显示未评分，不以零分参与均值 |
| T19 | 修订评分 | 留历史，但当前聚合只用最新有效评价 |
| T20 | 失败评价 | 能记录真实评价；无评价失败不自动变最低分 |
| T21 | 修改模型或强度 | 旧 Run 和评价仍指向旧行为快照 |
| T22 | 仅修改头像／名称 | 不改变模型行为，不重置质量记录 |
| T23 | 头像一致性 | 同 Profile 多实例使用同一头像，ID 可区分 |
| T24 | 敏感信息 | 日志、工单、导出中不出现凭据；只暴露授权产物 |
| T25 | 真实观测 | 无采集的成本、CPU、进度和 ETA 不伪造显示 |
| T26 | 产品范围 | 无游戏机制、职业人格、初始高级技能配置膨胀 |

其中数据归因、评分量表和存储实现属于建议规则；开工时写入小型 ADR 后再用作具体测试断言。

## 可以直接交给开发 Agent 的首条任务

> 阅读本包 README、冻结决策与 AGENTS.md。先完成 M0：在一个固定版本的 dsh 上验证两套执行配置，以及同 Profile 两个独立实例的启动、事件收集、取消和结果归因。交付运行时契约说明与可复现测试。不要修改核心产品范围，不做多 CLI，不写不存在的 SDK 方法，不先建复杂 UI。验证结束后按 M1、M2 推进。

## 每个实现阶段的交付记录

写清本次完成项、测试命令与结果、使用的 dsh 版本、配置差异、未实现项与阻塞。测试没有运行就标为未运行。界面截图只能证明展示，不替代后端验收。

涉及不可逆外部操作时，先保留显式授权边界，不将发布、合并或删除加入自动重试。运行时版本升级应重复核心契约测试。

# 施工 Agent 指南

本仓库／目录交接的是 **Lachesis** 的产品与架构基线，不是现成代码。先读 `docs/00_冻结决策.md`；最新明确用户要求高于原型图。

## 必须保持

- dsh-only；沿用插件式架构；不重写 LLM 调用与工具循环。
- 外部主 Agent 能提交任务，工单独立于其主会话生命周期。
- Profile 是可复用配置；多个实例可以来自同一 Profile。
- 初期行为配置只有供应商、模型、思考强度；名称和头像只是展示元数据。
- 头像绑定 Profile，同 Profile 的实例同头像，用实例 ID 区分。
- 评分属于工单，聚合到 Profile；不能按每次 Run 或实例重复刷评分。
- 生产力优先，不过度游戏化，不加入 AI 公司组织层级或养成系统。
- 「监工台」仅是设计方向词，不得进入产品名、页面名、导航、UI 文案、包名、仓库名或素材品牌。

## 开工顺序

先完成 M0，固定 dsh 版本并验证真实接口，再做数据、单工单闭环、并发恢复、验收评价与 UI。所有文档中的 Executor 方法、工具名、JSON 和类型均是应用草案，不是可直接调用的 dsh API。

实现建议可以调整，但应解释理由并更新 ADR。未定项不能被说成已经获得用户批准。不能擅自新建公开仓库、发布服务或产生外部付费操作。

## 工程约束

保持 Issue、Run、Instance、Session 与 Profile 的身份分离。不要用主 Agent 的内部子任务列表代替持久工单存储。不要通过全局模型切换、共享环境变量修改和进程全局工作目录变化管理并发。

执行结束只进入待验收。worker 不自验收、不自评分。幂等、领取、取消、重启校对和迟到结果保护必须可测。文件与日志不得泄露凭据。

原型中的职业标签、权重、进度百分比、模型名和统计是占位或冲突，不是实现要求；查 `docs/04_UI与原型纠偏.md`。

## 每次交付

提供变更摘要、验证命令与真实结果、版本与配置、已知限制以及下个可执行任务。没有测试就写未测试。不要把「模型说完成」或「UI 展示正常」当完整后端验收。
